# Troubleshooting

This document covers common KlipperPLR problems and diagnostic steps.

---

## `RESUME_INTERRUPTED` reports that no valid Z height is stored

Example:

```text
PLR: Keine gueltige Z-Hoehe gespeichert
```

KlipperPLR has not received a valid layer height from the slicer.

Verify that OrcaSlicer contains:

```gcode
LOG_Z Z={layer_z}
```

under:

**Printer Settings → Machine G-code → Before layer change G-code**

During a print, the Klipper console should show messages such as:

```text
PLR: Layer Z=0.8 gespeichert
```

If these messages never appear, check the generated G-code for:

```text
LOG_Z
```

---

## `LOG_Z: Parameter Z fehlt`

KlipperPLR received:

```gcode
LOG_Z
```

instead of:

```gcode
LOG_Z Z=<layer height>
```

New files should be sliced with:

```gcode
LOG_Z Z={layer_z}
```

Do not use the old parameterless form.

---

## Recovery layer cannot be found

The recovery script may report:

```text
PLR ERROR: Layer ;Z:<value> nicht gefunden.
```

KlipperPLR searches the original G-code for an exact layer marker such as:

```gcode
;Z:0.8
```

Check the original G-code:

```bash
grep -n '^;Z:' ~/printer_data/gcodes/<file>.gcode
```

Then compare those values with the stored recovery height.

The recovery height must correspond to a layer contained in the original sliced file.

---

## Wrong or old recovery height

If the saved `power_resume_z` belongs to an older print, recovery may fail or select an invalid layer.

The saved values can be inspected in:

```text
~/printer_data/config/save_variables.cfg
```

Do not edit this file while Klipper is running.

After a successfully completed print, use:

```gcode
clear_last_file
```

to reset the stored recovery information.

---

## Original G-code cannot be found

Example:

```text
PLR ERROR: Originaldatei nicht gefunden
```

KlipperPLR stores the original file path when:

```gcode
save_last_file
```

is executed.

Make sure `save_last_file` is part of the print start sequence.

Also verify that the original G-code has not been renamed, moved, or deleted since the interrupted print.

---

## X and Y do not home during recovery

During recovery, KlipperPLR intentionally restores only Z as a known axis:

```gcode
SET_KINEMATIC_POSITION Z=<saved_z> SET_HOMED=Z CLEAR_HOMED=XY
```

It then executes:

```gcode
G28 X Y
```

If X and Y do not physically home, inspect your Klipper homing configuration.

Custom configurations such as:

```ini
[homing_override]
```

may change the behavior of `G28`.

The printer must allow:

```gcode
G28 X Y
```

to actually home X and Y while leaving Z untouched.

---

## Printer tries to home Z during recovery

Stop the recovery immediately.

KlipperPLR must not physically home Z during normal recovery.

Check custom homing macros and `[homing_override]`.

A command such as:

```gcode
G28 X Y
```

must not indirectly trigger Z homing.

KlipperPLR expects Z to remain at the physical position retained from the interrupted print.

---

## X and Y appear homed although they were not homed

Using only:

```gcode
SET_KINEMATIC_POSITION Z=<saved_z>
```

is not sufficient for KlipperPLR's recovery procedure.

The recovery implementation uses:

```gcode
SET_KINEMATIC_POSITION Z=<saved_z> SET_HOMED=Z CLEAR_HOMED=XY
```

This explicitly keeps Z known while marking X and Y as unhomed.

If you have modified the recovery script, verify that this complete command is still present.

---

## Bed mesh cannot be loaded

KlipperPLR currently loads:

```gcode
BED_MESH_PROFILE LOAD=plr
```

If the profile does not exist, recovery cannot restore the expected mesh.

During normal print preparation, create and save the profile:

```gcode
BED_MESH_CLEAR
BED_MESH_CALIBRATE ADAPTIVE=1 ADAPTIVE_MARGIN=5
BED_MESH_PROFILE SAVE=plr
```

Your exact calibration command may differ depending on the printer configuration.

---

## `gcode_shell_command` is unknown

If Klipper reports an error involving:

```text
gcode_shell_command
```

verify that the extension exists:

```bash
ls -l ~/klipper/klippy/extras/gcode_shell_command.py
```

The KlipperPLR installer normally creates a symbolic link to:

```text
~/KlipperPLR/gcode_shell_command.py
```

After installing or changing this extension, restart Klipper.

---

## Shell script permission errors

Check the executable permissions:

```bash
ls -l ~/KlipperPLR/*.sh
```

The scripts can be made executable with:

```bash
chmod +x ~/KlipperPLR/*.sh
```

The installer normally handles this automatically.

---

## Recovery file was not generated

Check:

```text
~/printer_data/gcodes/plr/
```

From SSH:

```bash
ls -lah ~/printer_data/gcodes/plr/
```

If the directory or file is missing, inspect the Klipper console for messages beginning with:

```text
PLR ERROR:
```

Common causes include:

- missing original G-code
- invalid saved Z height
- no matching `;Z:` marker
- malformed `LOG_Z` commands
- shell-script execution failure

---

## Parameterless `LOG_Z` found in recovery file

Older sliced files may contain:

```gcode
LOG_Z
```

without a Z parameter.

During recovery generation, KlipperPLR attempts to convert these commands using the corresponding layer markers.

For example:

```gcode
;Z:1.2
LOG_Z
```

becomes:

```gcode
;Z:1.2
LOG_Z Z=1.2
```

Before accepting the generated recovery file, KlipperPLR checks for remaining parameterless `LOG_Z` commands.

If any remain, recovery generation is aborted rather than starting an invalid recovery print.

---

## Recovery uses the wrong temperatures

KlipperPLR determines temperatures from the original G-code before the recovery layer.

It searches for the most recent:

```gcode
M140
M190
M104
M109
```

commands.

If temperatures are controlled exclusively through unusual custom macros instead of standard G-code temperature commands, KlipperPLR may not be able to reconstruct them automatically.

Inspect the original G-code to verify how temperatures are set.

---

## Recovery starts but extrusion is incorrect

KlipperPLR distinguishes between relative and absolute extrusion.

Relative extrusion normally uses:

```gcode
M83
```

Absolute extrusion requires restoring the previous E coordinate using:

```gcode
G92 E<value>
```

If your slicer or macros switch extrusion modes multiple times during a print, inspect the generated recovery G-code before continuing testing.

---

## Update Manager does not show KlipperPLR

Verify that this file exists:

```bash
cat ~/printer_data/config/update_plr.cfg
```

It should contain a section similar to:

```ini
[update_manager KlipperPLR]
type: git_repo
path: /home/<user>/KlipperPLR
origin: https://github.com/HerrHaseGermany/KlipperPLR.git
primary_branch: main
install_script: install.sh
is_system_service: False
```

Then verify that `moonraker.conf` contains:

```ini
[include update_plr.cfg]
```

Restart Moonraker after changing its configuration.

---

## KlipperPLR commands are unknown

If commands such as:

```gcode
RESUME_INTERRUPTED
```

or:

```gcode
LOG_Z Z=0.8
```

are unknown, verify that `printer.cfg` contains:

```ini
[include plr.cfg]
```

Then check:

```bash
ls -l ~/printer_data/config/plr.cfg
```

Restart Klipper after correcting the configuration.

## Check the Git installation

To inspect the installed version:

```bash
cd ~/KlipperPLR
git status
git log --oneline -5
git remote -v
```

The main repository should point to:

```text
https://github.com/HerrHaseGermany/KlipperPLR.git
```

or the equivalent SSH remote.

---

## Inspect the generated recovery G-code

For difficult recovery problems, inspect the beginning of the generated file:

```bash
head -100 ~/printer_data/gcodes/plr/<file>.gcode
```

The beginning should contain the recovery setup before the original print continues.

You can also search for important commands:

```bash
grep -nE 'SET_KINEMATIC_POSITION|G28|BED_MESH|M109|M190|LOG_Z' \
~/printer_data/gcodes/plr/<file>.gcode
```

## Before reporting an issue

Useful diagnostic information includes:

```text
Klipper version
Moonraker version
Printer model
Controller board
Host system
Slicer and version
KlipperPLR version/commit
Relevant Klipper error message
Original G-code
Generated recovery G-code
Relevant printer.cfg sections
```

When reporting a recovery problem, describe whether it occurred during:

```text
Normal printing
Recovery-file generation
X/Y homing
Heating
Bed-mesh restoration
Position restoration
Actual resumed printing
```

This makes it much easier to identify which part of the recovery process failed.
